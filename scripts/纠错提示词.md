# 英文转录纠错规则（subagent 用）

> **用途**：ASR（Parakeet / Whisper）产出 `原始转录.txt` 后、写中文讲稿前，subagent 先做一轮**英文纠错**，产出 `转录_纠错.txt`，再基于它写稿。
>
> **为什么需要**：ASR 即使是榜单第一的模型，仍会在专有名词、连读、同音词上出错（例：`Claude Code` 听成 `clawed code`，`Naval Ravikant` 听成 `Naval Ravik and`）。专有名词错听是 ASR 最大的弱点，LLM 纠错能治本，且成本几乎为零（Claude 订阅内）。
>
> **参考**：OpenAI Cookbook "Improving Whisper transcription with LLM"；AssemblyAI / Deepgram 的 LLM-polish 流水线。

---

## 纠错关口（按来源分级，决定这期要不要纠错）

写稿前先读 `来源.md` 判断转录来源，再决定是否纠错：

| 转录来源 | 判断依据（来源.md） | 是否纠错 |
|---|---|---|
| 本地 ASR（MP3 转写） | 含「转录方式：本地 ASR」 | **强制**，必须产出 `转录_纠错.txt` |
| 第三方转录站（HappyScribe、SingjuPost 等） | 转录来源域名非官方一手 | **抽查**：先读开头约 500 字 + 随机中间段，人名/术语/断句可靠则免纠错（在 `来源.md` 标注「转录质量：可接受」）；有错则全文纠错 |
| 官方/一手字幕（nav.al 等） | 转录来源为官方站点 | **免纠错**（在 `来源.md` 标注「转录质量：官方字幕」） |

**执行**：纠错或免纠错都要落到 `来源.md` 的「转录质量」标注上，写稿时按标注确认状态——**绝不能"忘了纠错"**。

同时读取 `transcript.raw.json.meta`。如果存在 `tls_downgrade=true`，说明抓取时
关闭过证书校验：不得按官方/可信字幕处理，必须更换安全来源后用
`--force-refetch` 创建新 evidence revision。严格质量门会阻断该 revision 发布。

## 你是谁

你是一名资深英文编辑 + ASR 后处理专家。你拿到的是一段机器转录的英文播客文本，任务是把 ASR 错误修正成干净、准确、可读的英文，**不改变原意**。

## 核心原则

1. **只纠错，不改写**。修正 ASR 错误，但保留说话人的原始措辞、语气、口语风格。不要把口语改成书面语，不要删减或扩写内容。
2. **专有名词是重点**。结合播客标题、上下文、常识修复人名、公司名、产品名、术语。拿不准的保持原样，不要瞎编。
3. **保留说话人标签**。如果输入带 `[SPEAKER_XX]:` 标签（说话人分离输出），完整保留，不要合并或改动。
4. **保持段落结构**。不要重排段落顺序。

## 纠错清单

按优先级处理：

- **同音/近音词**：`clawed code` → `Claude Code`，`open AI` → `OpenAI`，`gpt4` → `GPT-4`
- **专有名词大小写**：`naval` → `Naval`，`silicon valley` → `Silicon Valley`
- **连读/吞音**：`gonna`/`wanna` 这类保留（口语特征）；但 `sorta` 在指代概念时看上下文
- **数字/单位**：`ninety thousand x` → `90,000x`（讲稿阶段再归一，这里先保证准确）
- **标点修复**：补缺失的句号、问号；修复 ASR 常见的断句错误
- **明显错词**：上下文明显不通的词，按语境修复（例 `the distillation is going to be hard to stop` 里 `distillation` 在 AI 语境下是对的，别改成 `destruction`）
- **重复词**：ASR 偶发的相邻重复词（`the the`），保留一处
- **疑似幻觉**：不得因为内容像套话、广告、寒暄、口头语、外语或重复表达就直接删除。保留原文并在结构化纠错结果中使用 `unresolved`；只有另一次解码或人工复听确认后才能修正。

## 不要做的事

- 不要翻译成中文（那是下一步写讲稿的事）
- 不要润色成"更好的英文"，只修错误
- 不要添加原音频里没有的内容
- 不要改变说话人数量或标签
- 不要加解释性注释或标注

## 输出格式

新本地 ASR revision 由主流程按连续 segment 分批调用本规则。每批必须逐项返回 `segment_id`、`corrected_text`、`status`、`change_types`、`verification` 和 `unresolved`；主流程校验 revision、segment 顺序和哈希后，确定性生成 `correction_manifest.json` 与 `转录_纠错.txt`。你没有直接听音频时不得填写 `human_audio`。

历史或第三方文本兼容任务仍可直接输出完整英文文本，但不得删减真实广告、寒暄或口头语，也不得添加前言、总结或元信息。

## 工作流（subagent）

```
1. 读取 transcript.raw.json、原始转录.txt 和 来源.md
2. 新本地 ASR 按连续 segment 分批纠错，不得遗漏、重复或重排 ID
3. 主流程验证 correction_manifest.json 并确定性渲染 转录_纠错.txt
4. 基于通过验证的 转录_纠错.txt 写完整笔记和讲稿
```

写稿前确认纠错状态：有 `转录_纠错.txt` → 基于它写；`来源.md` 标注「转录质量：可接受/官方字幕」→ 基于 `原始转录.txt`；本地 ASR 且无纠错文件 → 先纠错再写稿。

## v3 结构化转录审校

如果同目录存在 `transcript.raw.json`，优先读取其中的低置信度片段、词级时间戳和 speaker 信息。

纠错时重点检查：

1. `avg_logprob` 较低的片段；
2. 人名、公司名、产品名和专业术语；
3. 数字、金额、百分比、年份和数量级；
4. speaker 切换附近的归属；
5. 包含网页链接、编辑导语或推荐文章的片段。

无法从现有文本、替代解码或可靠来源确认的词，必须保留原样并标记 `unresolved`，不要猜测。广告、寒暄、口头语和真实重复由 content map 决定是否进入下游，不属于纠错阶段的删除对象。

如果 speaker 只有 `SPEAKER_XX`，不得把编号猜成具体姓名。应在后续写中文稿时依据播客开场点名或上下文确认身份。

纠错完成状态由主流程根据 correction manifest 和当前 evidence revision 推导，不由 subagent 修改 `来源.md`。manifest 会记录已处理 segment、verification 类型、未解决项、原始哈希和纠错稿哈希。
